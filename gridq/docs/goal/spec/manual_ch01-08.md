Places where the manual's claim looks inconsistent with what the code/tests show. Recorded only —
nothing was changed.

- **D1 — Dispatch sign convention (Ch 3 §"dispatch sign convention" vs `src/gridq/schemas/dispatch_profile.py`).** The manual states the persisted representative-day dispatch records one signed power number per half-hour (positive = discharge, negative = charge, "without consulting a separate flag"). The actual schema stores two separate non-negative series — `charge_kw: Field(ge=0)` and `discharge_kw: Field(ge=0)` (lines 36–37). No signed series exists on the contract, and no test asserts the manual's convention. Either the manual or the schema should change; as written, INV-M1-14 is untestable against the code.
- **D2 — Value accounting "sum equals reported total" (Ch 3).** The manual says "the sum of value across the streams must equal the reported total value. There is no slack line". `src/gridq/schemas/optimisation.py` appears to carry no `total_value` field to reconcile against (grep found none); totals are *derived* as sums downstream (`src/gridq/outputs/viewmodel.py:282`, `floor_total = round(sum(...))`), which makes the property true by construction rather than a validated contract invariant. The manual's phrasing implies a record-level reconciliation check that does not exist.
- **D3 — Baseline model version: "mock" vs "baseline" (Ch 6 Table pins vs Ch 7 Table baseline vs code).** Ch 6 gives the baseline engine's model version as `mock` ("e.g. `mock`, or a named solver-plus-formulation"); Ch 7's table and the code (`src/gridq/engine/baseline.py:127`, `model_version="baseline"`) both say `baseline`. Internal manual inconsistency; code agrees with Ch 7.
- **D4 — "gb_v0_1 is entirely placeholders" (Ch 5 plainnote) vs Appendix B status column.** Appendix B marks several gb_v0_1 entries `nr` (needs_review: perfect-foresight haircut, CM price/de-rating, Piclo price, gated streams, business rates) and says only "no value in this release is confirmed". "Entirely placeholders" in Ch 5 overstates it. Same-family nit: Ch 5's rebuild step 1 says "a value plus eight required descriptive fields" then lists eight fields *including* `value`.
- **D5 — The manual describes only `gb_v0_1`; the repo has moved to `gb_v1_0`.** Tests (`test_assumptions.py::test_gb_v1_0_*`) lock a gb_v1_0 release (0 confirmed / 10 needs_review / 15 placeholder per CLAUDE.md), including promotion/citation rules the manual never mentions. Appendix B is pinned to gb_v0_1 (fine, it is frozen), but chapters presenting gb_v0_1 as "the current release" are stale relative to the codebase.
- **D6 — Fixed reduction order for float sums (Ch 6 §"Fixed reduction order", rebuild step 5).** The manual claims every float reduction over a map (value-by-stream → total) iterates in canonical sorted-key order. Grep found no sorted-order accumulation on the value-summing paths (`outputs/viewmodel.py` sums a list in registry order; the only `sorted(` hit near finance is `assumptions_used=sorted(used)` in `finance/cashflows.py:547`, which sorts a name list, not a numeric reduction). Not a contradiction, but an untested normative claim worth a test.
